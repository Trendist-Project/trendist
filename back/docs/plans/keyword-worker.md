# 키워드 워커 설계 (2단계, 초안)

> 상태: **2a(`+`) 구현 완료.** 2b~2d는 아직 설계대로 진행하지 않았다. 구현 중 바뀐 점은 9절에 적었다.
> 선행: 1단계(킬·빼앗기 메모리 버퍼, `trendist.memory-player-counters`)와 키워드 카운터 메모리화(`trendist.memory-counters`).

## 1. 목적

키워드 한 개를 고치는 요청(`+`, 잃기, 빼앗기)이 DB 행 락(`keywords ... FOR UPDATE`)에서 줄을 서는 문제를 없앤다. 키워드마다 주인 워커 하나를 두고, 그 키워드를 바꾸는 요청을 큐로 순서대로 처리한다.

## 2. 현재 구조 (코드 확인 결과)

`KeywordServiceImpl.plus()`는 한 `@Transactional` 안에서 다음을 한다.

| 순서 | 작업 | 잠금 |
|---|---|---|
| 1 | 플레이어 조회 | `players` FOR UPDATE |
| 2 | 키워드 조회·생성, 금지 확인 | `keywords` FOR UPDATE |
| 3 | 보관함 중복 확인 (`holdings`) | 없음 |
| 4 | 보관함 INSERT 또는 만료 행 재사용 | 없음 |
| 5 | 키워드 카운터 증가, 활성 전환 | 메모리 `KeywordCounters` (`synchronized`) |
| 6 | 플레이어 EXP, 보관함 수, 점수 재계산 (`recompute`) | 플레이어 행 (1번에서 잡음) |
| 7 | 결과 카드·요약 생성 후 HTTP 응답 | 트랜잭션 종료 때 해제 |

잠금 순서는 "플레이어 → 키워드"다. 잃기·빼앗기도 두 플레이어와 키워드를 같은 순서(번호 순)로 잠근다.

**키워드 행 잠금이 실제로 보호하는 것**: 같은 키워드에 대한 동시 `+`의 중복 검사(3번)와 상태 전환(활성·금지). 카운터 자체는 이미 메모리 `synchronized`로 보호된다.

## 3. 제안: 키워드 소유 워커

### 3.1 소유 규칙

- 키워드 번호 `id`에 대해 담당 워커는 `workers[id % N]`이다. `N`은 설정값 `trendist.keyword-workers`(기본 = CPU 코어 수, 최소 2).
- 키워드의 **상태 변경**(보유 확인·추가·제거, 활성·금지 전환, 키워드 카운터 증가)은 담당 워커 스레드만 한다.
- 플레이어의 **보관함 행, EXP, 점수**는 플레이어 쪽이 한다. 접속 중이면 그 방 틱 큐로, 아니면 기존처럼 DB 트랜잭션으로.

### 3.2 `+` 흐름

```
HTTP 스레드                     키워드 워커 (담당)                 플레이어 쪽 (DB 트랜잭션)
─────────────────────────────────────────────────────────────────────────────────────────
1. 요청 접수, 입력 검사
2. 워커 큐에 PlusReq(id, playerId, requestId) 넣고 Future 대기
                                 3. 중복 확인: 워커 메모리의 보유 집합
                                    (playerId, keywordId) — 없으면 통과
                                 4. 키워드 카운터 +1, 활성 전환 판단
                                 5. Future에 PlusDecision(keywordId, newHolder, expires) 완료
6. Future 결과로 플레이어 트랜잭션 시작 ─────────────────────────────────────────────────▶ 7. players FOR UPDATE
                                                                                       8. holdings INSERT/재사용 (requestId 기록)
                                                                                       9. p.incHold/incAdd/addExp, recompute
                                                                                      10. 커밋
11. 응답 (카드·요약)
```

- **중복 방지의 근거는 워커의 메모리 보유 집합**이다. DB의 `holdings` 조회는 워커가 하지 않는다.
- 플레이어 쪽 단계 (7~10)가 실패하면 워커에 **보상 요청**(`UndoPlus(requestId)`)을 보내 카운터와 보유 집합을 되돌린다.

### 3.3 실패와 보상

| 실패 지점 | 처리 |
|---|---|
| 워커 결정 전 (3~5) | 결과 없음. 클라이언트에 오류 응답, 아무것도 바뀌지 않음 |
| 워커 결정 후, 플레이어 쪽 전 (7~9) | 워커에 `UndoPlus(requestId)`. 워커는 requestId로 결정을 찾아 되돌림 (멱등) |
| 플레이어 쪽 커밋 후 응답 전 장애 | 재시도 시 같은 requestId면 플레이어 쪽이 `holdings`의 requestId를 보고 이미 처리됨을 알림 |
| 서버 강제 종료 | 워커 메모리는 사라짐. 시작할 때 `holdings`에서 보유 집합을 다시 만든다 (기존 `MemoryHoldings` 시작 보정과 같은 방식) |

**멱등성**: 모든 요청은 `requestId`(UUID)를 가진다. `holdings`에 `request_id` 열(마이그레이션 필요)을 두고 같은 요청이 두 번 들어와도 한 번만 반영한다.

### 3.4 잃기·빼앗기

- 잃기(`loseFraction`, `loseAll`): 워커마다 "이 키워드 보유자 X를 제거"를 요청한다. 제거는 워커에서 결정하고, 플레이어 쪽에 `holdings` 삭제와 점수 재계산을 보낸다.
- 빼앗기: 키워드 워커가 "소유자 A → B"를 결정하고, A·B 플레이어 쪽에 각각 메시지를 보낸다. 두 플레이어 쪽은 번호 순으로 잠근다(기존 규칙).
- **무작위 선택**(`findByIdForUpdate(random)`)은 워커 큐에서 "후보 중 하나 선택"을 워커가 직접 하도록 옮긴다.

### 3.5 HTTP 대기와 교착

- `+`의 HTTP 스레드는 **플레이어 잠금을 쥐기 전에** 워커 결과를 기다린다. 따라서 플레이어 행 잠금을 쥔 채 워커를 기다리는 구간은 없다.
- 워커는 플레이어 잠금을 기다리지 않는다. 워커 안에서는 DB 호출을 하지 않는다(메모리 계산만). 저장은 워커가 결정한 뒤 별도 경로다.
- 워커 대기 시간 상한(예: 2초)을 두고, 넘으면 오류 응답 후 requestId 기준으로 상태를 확인한다.

## 4. 단계별 범위

| 단계 | 대상 | 완료 기준 |
|---|---|---|
| 2a | `+` (플레이어 쪽은 기존 트랜잭션 유지, 키워드 쪽만 워커) | 동시 `+` 100건에서 중복 보유 0건, 보관함 수 = 행 수, 실패 주입 시 보상 확인 |
| 2b | 잃기(`loseFraction`, `loseAll`) | 불꽃·사망 잃기 후 보유 수와 DB 행 수 일치 |
| 2c | 빼앗기(`steal`, 충돌) | 두 플레이어 동시 빼앗기에서 키워드 소유자가 항상 한 명 |
| 2d | 무작위 선택(잃기 대상, 구슬) | 워커 안에서 선택, DB 행 락 없음 |

한 단계가 끝나면 로컬 실행과 `PerfProbe`로 확인한 뒤 다음 단계로 간다.

## 5. 롤아웃

- 플래그 `trendist.keyword-workers=true`로 켠다. 꺼져 있으면 지금의 `plus()` 경로를 그대로 쓴다. 단계별로 플래그를 나눈다(2a는 `trendist.keyword-worker-plus`).
- dev에서 켜고 검증한 뒤 prod에서 켠다.

## 6. 테스트 계획

- 단위: 워커의 중복 검사, 결정·되돌리기 순서, requestId 멱등성.
- 통합(H2): 같은 키워드에 여러 플레이어가 동시에 `+`해도 `holdings` 행 수 = 카운터 = 보유 집합.
- 장애 주입: 플레이어 쪽 트랜잭션을 실패시켜 `UndoPlus`가 카운터를 되돌리는지.
- 회귀: 기존 `KeywordMergeTest`, `KeywordCountersTest`, `MemoryHoldingsTest`가 계속 통과.

## 7. 열린 질문

1. **워커 수 기본값**: 코어 수로 할지, 고정 8로 할지.
2. **HTTP 대기 상한**: 2초가 적당한지. 초과 시 클라이언트 재시도를 허용할지.
3. **`holdings.request_id` 열**: 마이그레이션(Flyway)을 추가해도 되는지. 없이 하면 멱등성을 메모리 requestId 집합으로만 보장해야 하고, 재시작 후 중복 방지가 약해집니다.
4. **2a를 먼저 할지, 측정(1단계 효과) 결과를 보고 2a를 할지.**

## 8. 위험

- 워커 메모리와 DB 보유 행이 어긋나는 구간(플레이어 쪽 커밋 전)이 생긴다. 보상과 시작 시 재구성으로 복구하지만, 이 구간의 조회는 "집계 중" 같은 임시 상태를 보일 수 있다.
- 서버 1대 전제다. 여러 대가 되면 워커 소유권을 서버 간에 나눠야 한다(Redis 또는 샤딩).

## 9. 구현 기록 (2a)

승인된 설계(3절, 플레이어 쪽과 키워드 쪽을 메시지로 나눔)에서 **한 가지를 바꿨다.** `+` 트랜잭션 전체를 키워드 워커 스레드에서 실행한다.

- **이유 1**: `Keyword` 엔티티에 `@DynamicUpdate`가 없어서, 키워드 행 잠금을 빼면 트랜잭션 시작 때 읽은 값으로 행 전체를 다시 써서 다른 경로가 바꾼 열을 덮어쓸 수 있다. 그래서 `@DynamicUpdate`를 붙였다.
- **이유 2**: 나눈 방식은 보상 로직이 필요하지만, 한 트랜잭션이면 실패는 롤백으로 끝난다. 정합성이 더 단순하다.
- **결과**: 같은 정규화 이름의 `+`는 같은 워커에서 줄을 서므로 키워드 행 잠금 없이도 중복 검사와 생성이 직렬이다. 플레이어 행은 기존처럼 잠근다.

구현 위치:

- `keyword/worker/KeywordWorkers`: 워커 배열(수 = `trendist.keyword-workers`, 0이면 코어 수, 최소 2). `call(key, task, wait)`는 대기 2초를 넘기면 `KEYWORD_BUSY`(429)를 던지고, 아직 시작하지 않은 작업은 취소한다.
- `KeywordServiceImpl.plus()`: 입력 검사 후 워커에서 `plusInLane()`을 트랜잭션으로 실행한다. 키워드 행 잠금(`findByIdForUpdate`)을 쓰지 않는다.
- `player_keywords.request_id`(V86): `+` 요청 번호를 남긴다. 중복 방지에는 쓰지 않는다(한 트랜잭션이라 불필요). 로그와 행을 잇는 추적용이다.

운영상 알아 둘 점:

- **플래그가 없다.** 설계의 `trendist.keyword-worker-plus` 플래그는 만들지 않았다. 되돌리려면 커밋을 되돌린다.
- **`KEYWORD_BUSY` 뒤의 재시도**: 워커가 이미 시작한 요청은 대기 시간이 지나도 끝까지 실행된다. 클라이언트가 다시 보내면 `ALREADY_PLUSED`(409)가 올 수 있다. 재시도 시 409는 "이미 추가됨"으로 읽어야 한다. 요청 번호를 클라이언트가 보내는 방식(멱등 키)은 다음 단계 후보다.
- **DB 연결**: 워커 수만큼 연결을 동시에 쓴다(코어 수, 보통 8 이하). 방의 DB 작업 상한(4)과 합쳐도 연결 풀(20) 안에 들어간다.
- **외부 확인**: 새 키워드를 만들 때 `externalConfirm`(외부 조회)이 워커 안에서 실행된다. 느리면 같은 워커의 다른 키워드 `+`도 기다린다.
- **다른 경로와의 경쟁**: 금지 여부(`isBanned`)는 잠금 없이 읽는다. 관리자가 금지하는 순간과 `+`가 겹치면 드물게 금지된 키워드가 한 번 더해질 수 있다.
- **이름이 같은 키워드를 다른 경로가 동시에 만들면** 유니크 제약에서 한쪽이 실패한다(이 경우 `+`는 500). 기존에도 있던 경쟁이며, 재시도로 고치는 것은 후속 작업이다.

테스트:

- `KeywordWorkersTest`(4개): 같은 키의 작업은 한 스레드에서 순서대로, 증가 누락 없음, 예외 그대로 전달, 대기 초과 시 `KEYWORD_BUSY`.
- `KeywordPlusConcurrencyTest`(2개): 게스트 12명이 같은 새 키워드를 동시에 더하면 모두 성공하고 보유 수와 행 수가 12, 한 명이 6번 동시에 더하면 성공 1, 충돌 5.
- 전체 테스트 48개 클래스 통과.
